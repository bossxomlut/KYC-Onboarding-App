# Shared implementation contracts

## HTTP

Base `/api/v1`. JSON camelCase. Errors `{error:{code,message,requestId}}`. Bearer access tokens. Auth routes: register `{email,password}` -> `{user,nextStep:"VERIFY_EMAIL"}`; email/verify `{email,code}` and login `{email,password}` and refresh `{refreshToken}` -> `{user,accessToken,refreshToken,expiresIn:900}`. me -> `{user}`. Public users include `{id,email,emailVerified,role}`; role is `user`, `reviewer` or `super_admin`, read live from the database. email/resend and password/forgot -> `{message}`. password/reset `{token,newPassword}`. logout `{refreshToken}`.

Login with valid credentials for an unverified email creates and attempts delivery of a verification OTP before returning `403 EMAIL_NOT_VERIFIED`; the client opens email verification without a manual resend. Login and resend share the 30-second OTP creation cooldown. Failed mail delivery remains in the encrypted outbox for retry. Invalid credentials, disabled users, and verified users do not trigger verification mail.

## KYC

GET `/kyc` -> `{profile: {...}}`; PUT `/kyc/personal-details` body `{fullName,dateOfBirth,nationality,address,documentNumber}`; POST `/kyc/media/:kind` multipart field `file`, optional `captureId` (16–128 URL-safe characters) to correlate/retry interrupted captures; document also `documentType` (`passport`,`national_id`,`driving_licence`), kinds `document`, `selfie`; GET `/kyc/media/:kind` authenticated bytes. POST `/kyc/submit`, POST `/kyc/resubmit` -> `{profile}`.

Profile: `{id,status,nextStep,personalDetails,document,selfie,rejectionReason,requiredSteps,submittedAt,updatedAt}`. Status `not_started`, `in_progress`, `pending_review`, `verified`, `rejected`. Step `personal_details`, `document`, `selfie`, `review`, `result`. PersonalDetails nullable uses fields above. Media nullable `{id,mimeType,size,documentType?,captureId?}`. On resubmit clear required rejected assets, preserve accepted data, transition in_progress and derive nextStep. Updates disallowed when pending_review/verified/rejected until resubmit. Review results are set by authenticated reviewer/super_admin accounts through `/reviews/:userId/decision`; self-review is forbidden and every new decision records its actor.

Optional OCR/face comparison adds `verification` to profile responses. `POST /kyc/verification` has no applicant-supplied identity or media IDs and returns `{profile}`. It requires an editable profile and both uploaded images; missing provider returns `503 VERIFICATION_NOT_CONFIGURED`. Checks run only on this explicit action. Same-image completed checks are cached; failed checks may retry after 30 seconds. In-flight duplicate requests and submission are rejected until the bounded attempt finishes or expires. Image replacement invalidates working evidence; idempotent capture-ID retries preserve it. Cloud IO occurs outside database transactions and final persistence requires unchanged source IDs and an editable profile. Results never automatically approve/reject KYC or overwrite personal details.

Verification: `{provider:"aws"|"none",status:"disabled"|"not_started"|"completed"|"failed",documentId,selfieId,checkedAt,ocr,faceMatch}`. IDs/time are nullable when checks have not run; both results are nullable. OCR `{status:"succeeded"|"no_text"|"failed",text,fields:{fullName,dateOfBirth,documentNumber},confidence}` has nullable fields/confidence. FaceMatch `{status:"matched"|"not_matched"|"no_face"|"multiple_faces"|"failed",similarity,threshold}` has nullable similarity. Any failed component makes overall status failed; other semantic outcomes are completed. Exactly one face in each image is required for comparison. Similarity is a 0–100 score; threshold is configuration, not approval policy. Working encrypted evidence is copied into the immutable submission on submit and is exposed through reviewer/detail/history profiles. Legacy snapshots may have null evidence; existing stored evidence remains readable when new checks are disabled. Migration006 adds nullable encrypted result and attempt/cooldown columns. See [provider setup](../identity-verification.md).

Each submit stores a separate submission version with encrypted personal details and immutable references to the submitted document/selfie files. Editing a reopened profile changes only the working profile; previous submissions and their photos remain available. Pending submit retries do not create another version. Each new decision records the authenticated reviewer's ID, email and role at decision time, review time, decision, reason and requested corrections. Reviewer identity is never accepted from the request body.

GET `/kyc/history?limit=20&offset=0` lists only the authenticated applicant's submissions, newest version first. GET `/reviews/:userId/history` provides the same history to a live reviewer/super_admin for another user, including after a decision. Both return `{submissions:[{id,version,profile,review}],total}`. Profile is the original submitted snapshot with `nextStep:"result"`, its submission status and decision metadata. Review is nullable or `{decision,reason,requiredSteps,reviewedAt,reviewer}`; reviewer is nullable or `{id,email,role}`. Legacy audits may retain a known reviewer ID with null email/role because those values were not previously captured. A legacy final profile without a matching audit has a null review; no review time is invented. Lists use limit20 by default, maximum100, and nonnegative offset.

GET `/kyc/history/:submissionId/media/:kind` and GET `/reviews/:userId/history/:submissionId/media/:kind` return the original authenticated image with `Cache-Control: no-store`. The submission must belong to the authenticated applicant or the explicitly authorized review target. Metadata never exposes storage keys. Existing current-profile media routes keep their contracts. Migration 005 preserves the currently surviving submitted profile and matching latest audit; earlier versions or files already deleted before this feature cannot be reconstructed.

## Flutter shared contracts

Paths use `lib/core`, `lib/features`, `lib/app`. `core/domain/result.dart`: sealed `Result<T>` with `Success<T>(value)`, `Failure<T>(AppFailure error)`; `AppFailure` fields code/message and getter isNetwork. Pure Dart.
`core/network/api_client.dart`: ApiClient(Dio dio), methods get/post/put returning decoded `Map<String,dynamic>`, upload(path,filePath,{fields}), bytes(path), and public Dio get dio. Shared network/auth data layers implement token storage and retry.
`core/security/token_store.dart`: TokenStore interface `Future<String?> readRefreshToken()`, `Future<void> saveTokens({required String accessToken,required String refreshToken})`, `Future<void> clear()`, `String? get accessToken`; SecureTokenStore implementation. Optional `ConditionalTokenStore.clearIfUnchanged({required String? expectedRefreshToken})` compares and clears atomically under the same storage queue as save/rotation. A delayed password-reset success cannot clear a newer login's credentials. No persistence of PII in plaintext.
AuthSessionCubit is app-scoped; KycCubit is authenticated applicant-flow scoped for user/reviewer. Super admins have a separate Home with management/review actions and bypass the applicant KYC provider and profile fetch; `/kyc/*` redirects them home. Root DI/router may compose these roles without feature flow-to-flow imports. Auth repository exposes use cases consumed by auth cubits. KYC repository/use cases consume ApiClient. KYC status colors/icons belong to presentation; the status entity remains pure Dart.

Document/selfie capture uploads automatically but stays on the capture page with an in-memory photo preview. Only the user's Continue action navigates to the server-derived `nextStep`; it requires an editable profile, confirmed uploaded media, no pending replacement for that kind, no operation in progress, and a next step beyond the current page. A successful upload retry also stays on the current page. Retaking remains available before continuing.

Home pushes authenticated features and stays in the navigation stack with its existing KYC flow state. Toolbar/system Back pops to the page that opened the feature; history returns to its originating status/reviewer page and reviewer detail returns to its queue. KYC step transitions replace the active KYC page while retaining Home underneath. Direct feature/deep-link entry without a previous page falls back to Home, including KYC loading/error screens. Open dialogs and bottom sheets consume Back first; Home lets the operating system handle Back. The shell always keeps its Navigator mounted and owns the KYC Cubit; page guards handle profile availability and redirects inside each route. Async page actions navigate on completion only while their original route is still current, so completing a save/submission/review after Back does not leave the page the user returned to. A retained reviewer queue refreshes at its current offset after returning from detail.

Submission history uses its own route-scoped factory Cubit and history use cases. `/kyc/history` stays accessible for applicant statuses including rejected, in_progress and verified; it does not reopen the profile or alter the KYC flow. Home and verification status link to applicant history; reviewer detail links to `/reviews/:userId/history` for comparison. Selected versions open a read-only sheet with original details, private photos and review information. Photo bytes remain in route-local memory and are cleared on authorization failure or disposal.

The app root owns one lifecycle observer. A `hidden`/`paused` → `resumed` cycle checks `/auth/me` before refreshing the current authenticated route; a focus-only `inactive` → `resumed` does not reload. Retained routes mark their data stale on background and refresh when revealed after Back; ordinary push/pop does not reload Home. Reveal refresh waits for Router to report the popped stack before starting session revalidation. Session revalidation keeps the authenticated subtree mounted, updates live roles and checks the active pushed route for revoked permissions. Current-route checks use the active router state and page identity, so a popped page's delayed action cannot redirect another visit to the same URI. Network failure keeps the page/draft with a Retry banner. New background cycles and newer server-derived user updates invalidate older permission checks without changing the session/provider scope.

Foreground KYC refresh is a GET reconciliation: it preserves unsaved form state and local photo previews, coalesces concurrent profile reads, and queues one read after an in-flight capture/upload/write. It never repeats a submit, resubmit, OTP resend, or administrative decision. Media-ID changes invalidate cached photos; an open Review/summary loads changed media. Operation state distinguishes camera, upload and profile/media reads, and read Retry targets the failed read. Access screens disable mutations until their foreground data is revalidated and retain their current page offsets. History refresh reconciles the loaded pages while keeping the selected immutable submission, its photos and open sheet.

Email verification uses a 30-second absolute resend deadline, seeded only after a known OTP-issuing login/register response, and reconciles remaining time on resume. A warm reset-password link with a different token replaces the token, clears the old password draft and ignores completion from the previous form operation for UI state. Successful reset completion still invalidates its original app session independently of form lifetime; a later login is preserved. Ordinary background transitions preserve in-memory drafts; process termination still restores only saved server progress and supported private capture recovery.

## Access and reviewer APIs

Public registration accepts only email/password and always creates `user`. One operator-only bootstrap creates the initial `super_admin`; management APIs permit only `user`/`reviewer` assignments and protect the owner. See [admin guide](../admin-access.md).

GET `/access/role-request` -> `{request:null|{id,userId,email,status,reason,decisionReason,createdAt,decidedAt}}`; POST same `{reason}` -> `{request}` (201), one pending request per user. GET `/admin/users?limit=50&offset=0` -> `{users:[{id,email,emailVerified,role,createdAt}],total}`; POST `{email,password,role}` -> `{user,nextStep:"VERIFY_EMAIL"}` (201). PUT `/admin/users/:userId/role` `{role,reason?}` -> `{user}`. GET `/admin/role-requests?status=pending&limit=50&offset=0` -> `{requests,total}`; POST `/admin/role-requests/:id/decision` `{decision:"approved"|"rejected",reason?}` -> `{request,user}`. Only super_admin can manage accounts/requests.

GET `/reviews?status=pending_review&search=&limit=50&offset=0` -> `{profiles:[{userId,email,status,submittedAt}],total}`. Status is `pending_review` (default), `verified`, `rejected`, or `all`; all includes those three current profile statuses and excludes unsubmitted/in-progress profiles. Search is a trimmed, case-insensitive literal email substring, at most254 characters; `%`, `_` and backslash are ordinary search characters. Filtering/search run before pagination, and the returned total uses the same filters and database snapshot as the page. Lists exclude the actor's own profile and sort by submittedAt then userId, ascending.

GET `/reviews/:userId` -> `{submissionId,user:{id,email},profile}` where profile/photos describe that immutable submitted version. GET `/reviews/:userId/media/:kind?submissionId=<uuid>` -> authenticated JPEG bytes, no-store; POST `/reviews/:userId/decision` `{submissionId,decision:"verified"|"rejected",reason?,requiredSteps?}` -> `{profile}`. Both media and decision require the returned submission ID. A different current pending submission returns `409 KYC_REVIEW_CHANGED` before any decision/audit write; the client must reload and review that version. Reviewer/super_admin only; detail/media require another user's pending profile. Completed list entries open `/reviews/:userId/history?from=queue` to view the original submissions and decisions read-only. The review-list Cubit retains filters/search for refresh and pagination, resets offset when criteria change, and discards responses from older queries. Pushed detail/history routes retain the list state on return. Rejection needs reason3–1000 and nonempty requiredSteps; verified has no correction steps. Roles are checked in the guard and inside privileged transactions. Lists default50/max100. Admin request statuses pending/approved/rejected. Role request reason10–1000; optional management reasons1–1000.

Backend and mobile must be released together for this reviewer contract: older clients that omit submissionId receive validation400. No database migration is required beyond the existing submission-history migration005.

Access feature Cubits are route-scoped factories. AuthSessionCubit accepts a server-derived user update as an app-scoped contract; access does not read or coordinate KYC flow state. Reviewer photos remain in route-local memory and are cleared on authorization failure.
